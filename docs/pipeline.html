Build, test & publish

Astrava uses a tiered pipeline: run inexpensive checks on every change, apply browser checks according to risk, and publish the exact artifact that passed. Delivery verification is deliberately smaller than engine regression.

Source of truth: .github/workflows/pages.yml, validation.yml, renderer-diagnostics.yml, and scripts/ci/. This page describes their implemented behaviour. It does not claim hardware performance, exhaustive visual correctness or configured branch protection.

1. End-to-end flow

Pull request / push to main / manual run │ Fast checks + change classification │ Build dist exactly once │ Static links + per-file SHA256 manifest │ Sealed astrava-site / site.tgz artifact │ ┌────────┴──────────────────────┐ │ │ Production WebGPU smoke Full terrain when required (quick or full profile) edges │ corners+morphs │ flight+budgets │ │ └───────────────┬───────────────┘ Validation gate │ Main only: verify and publish SAME artifact │ Published commit + manifest + asset hashes │ One fresh-browser visible-planet check

Documentation-only changes skip pre-publication browser jobs but still run all behavioural tests, build validation and the post-publication browser check. Engine, pipeline and unknown changes run the full pre-publication suite. PR validation never publishes.

There is no separate exhaustive workflow on every feature-branch push. Open a PR to receive CI, or run full regression manually. This avoids running a feature push suite and an identical PR suite at the same time. A merge result is a new commit and is validated again; this pipeline does not reuse approvals from a different PR artifact.

3. Conservative test selection

scripts/ci/plan.mjs produces .ci/plan.json and tier outputs. Only explicitly recognised lower-risk paths may receive a reduced test plan. A mixed change takes the most demanding tier.

TierPaths / conditionsRequired pre-publication checks
docsREADME.md, LICENSE, .gitignore; docs files ending html, md, png, svg, jpg or webp; or an empty known diffAll fast tests, build and static links/imports. Browser smoke and terrain jobs intentionally skip.
smokeKnown marketing/demo HTML pages; src/styles.css; src/site.js; supported image assets; engine/demo.cssFast tests plus quick production WebGPU smoke. These files can affect canvas layout or startup links.
fullEngine code and WGSL, build/test scripts, dependencies/lockfile, workflow YAML, all other unclassified paths; unknown baseline; force_full=trueFast tests, full production smoke/recovery and all three terrain groups.

No material-only exception exists yet. The current planet shader combines vertex and fragment work, so every change to it receives full validation. Moving shading into independent modules does not automatically grant an exemption: add a reviewed classifier rule and tests first.

Baseline handling prevents skipped-commit gaps

For a PR, classification uses the merge base between the PR base SHA and the checked-out test commit. On main, it compares HEAD with the actually published commit from the public build-info.json, not merely the push event's previous SHA. This catches engine changes from intermediate queued, failed or superseded pushes even when the latest commit edits only documentation.

The baseline must be a 40-character hexadecimal commit, exist in the full checkout and be an ancestor of HEAD. A missing manifest, network failure, rewritten history or invalid SHA selects full validation. Deletions and renames are included by diffing paths without rename collapsing. Local classification can use ASTRAVA_BASE_COMMIT; uncertain input never silently downgrades testing.

4. Test levels and exact coverage

Fast checks: every validation run

npm run check checks JavaScript syntax and runs every tests/*.test.mjs suite. Existing depth, frame-pacing, buffer-layout, cross-face topology, balancing, partition coverage and morph endpoint tests remain intact. Pipeline tests additionally verify tier classification, fail-closed gates, the 67-case partition, artifact corruption detection and browser-version/workflow consistency.

After building, scripts/ci/site-check.mjs walks generated HTML and JavaScript. Local href/src targets and relative module imports must resolve inside the release. This detects missing documentation pages and versioned modules without launching a GPU. It is not a complete accessibility audit, semantic HTML validator, or remote-link checker.

Production browser smoke

ProfileAssertionsUse
quickNormal startup submits real frames; visible shaded orbit; near orbit at production budget; a real seam transition at alpha 0.5 and its completed endpointPresentation/integration changes
fullQuick checks plus cache-cleared reload, larger viewport, reset control, invalid-WGSL visible error and unsupported-WebGPU visible errorEngine/tooling changes and exhaustive runs
deliveryFresh browser, correct build and versioned asset graph, GPU/JS health and a visible production-shaded planetAfter publication, including documentation-only releases

Orbit checks require a nonblank shaded object against space. Nadir near-orbit checks require more than 99% non-clear coverage and shading diversity. Every successful frame also requires a running engine, nonzero bounded tiles, logical-cut and GPU-capacity compliance, and no unexpected GPU, JavaScript or resource-loading errors. An intentionally injected shader failure is handled separately and is expected to show an error rather than report online.

Full terrain regression: 67 cases, three isolated jobs

GroupCasesCoverage
edges24Both sides of all twelve cube edges
corners-morphs19Eight corners and eleven transition factors from 0 to 1
flight-budgets24Descent/ascent through five altitudes at three factors; budgets 6, 24 and 96 at three factors

Each job creates its own browser, initial orbit and 96-tile logical budget. No job depends on the last camera pose of another job. The test catalogue is scripts/testing/terrain-cases.mjs; a unit test verifies exactly 67 unique labels across the groups. One browser runs per runner, with up to three terrain runners in parallel. Fail-fast is disabled so a failure in one group does not erase evidence from the others.

Terrain coverage executes the real production vertex shader, including displacement, stitching and morphing. Only the fragment output is replaced with a flat diagnostic colour, preventing dark oceans or night-side lighting from being counted as missing geometry. Each capture must exceed 99.9% coverage. Production shading is tested independently by the smoke job. Pixel tolerances are deliberate: the tests detect substantial holes, not mathematical perfection at every rasterised edge.

5. How frame stepping reduces wasted rendering

scripts/testing/browser-harness.mjs initially allows the ordinary requestAnimationFrame loop to run. After verified startup and at least two frames, the harness pauses scheduling, drains already-submitted GPU work, and stores subsequent frame callbacks. Each assertion explicitly executes the next callback, waits for its GPU work to complete, and captures the canvas while production scheduling remains paused.

The simulation seed, inspection pose and morph factor remain controlled through the existing diagnostics interface. The engine's renderer is unchanged; the harness controls browser scheduling, not terrain geometry. This removes continuous redraw while Playwright evaluates DOM state, captures PNGs and computes coverage. It also stops the tests waiting for an element to appear stable while an expensive game loop competes for resources.

Current limitation: coverage still uses canvas screenshots and PNG decoding. Direct GPU-target readback is not implemented. We save one representative PNG per group/profile, all JSON measurements, and failure images; set ASTRAVA_SCREENSHOTS=all for every successful image. Fewer saved files reduce storage, while explicit frame scheduling and job parallelism provide the main elapsed-time reduction.

6. Build-once and artifact integrity

The prepare job builds dist/ exactly once, after fast checks. The existing build isolates the engine dependency graph under runtime/<commit>/engine/, writes the matching build-info module and public build-info.json, and points demo.html at those exact script and shader paths.

scripts/ci/artifact.mjs pack creates artifact-manifest.json containing the commit and SHA256 of every regular release file, excluding the manifest itself. Symlinks are rejected. It then packages the tree as .ci/site.tgz, hashes that archive and the manifest, and exposes both hashes as job outputs. .ci/release.json records these identities.

Smoke jobs, terrain jobs and the deployment job download the same astrava-site artifact from the same workflow run. Before using it, they check the archive hash, unpack it and verify the manifest hash, commit, complete file set and each file's content hash. A mismatch is an error, not a warning. They do not call the build script again.

The Pages upload action wraps the verified directory in its own deployment format; no application rebuild occurs. Seven-day artifacts are convenient reproducibility evidence, not permanent releases or cryptographic author attestations. Checksums protect identity relative to the trusted producing job; they do not make malicious source code trustworthy.

7. Gates, skips and permissions

The stable Validation gate job runs with if: always(). A docs plan permits deliberately skipped smoke/terrain jobs. A smoke plan requires smoke success. A full plan requires smoke success and success from the complete terrain matrix. Prepare must always succeed. Missing plans, unexpected skips, failures and cancellations fail the gate.

Normal validation jobs have contents: read. Only the main deployment job receives pages: write and id-token: write, and it uses the github-pages environment. Checkout credentials are not persisted. No repository write token, external service secret or self-hosted machine is needed by tests. PRs run on ephemeral GitHub-hosted runners and cannot deploy through this workflow.

Configure branch rules separately to require the displayed Validation gate check before merge. The workflow does not itself create or claim branch protection. A maintainer with permission to alter workflows can alter the gate; protect those files with review policy as the team grows.

8. Delivery verification and caching

Main runs are serialised without cancelling an active deployment. A newer pending run may replace an older pending run in GitHub's concurrency queue; comparing against the published baseline prevents a resulting classification gap. Superseded PR runs may be cancelled because they cannot publish.

After deployment, scripts/ci/published.mjs polls for the expected commit with cache-busting queries, bounded request timeouts and an approximately three-minute retry window. The served manifest must match the tested manifest hash. It additionally fetches and hashes demo.html, the shared stylesheet, the versioned boot module, main module and planet WGSL against manifest entries. This is sampled delivery integrity, not a second full-file download.

A new browser then runs the delivery profile. Its requested engine files must use the expected versioned path and it must actually render the planet. The full terrain and recovery suites are not repeated on Pages. A post-deployment failure makes the workflow red but cannot undo an already completed publication. There is no automatic rollback.

9. Reproducible test environment and costs

Test dependencies are committed in package-lock.json and installed with npm ci --ignore-scripts. The current Playwright package is 1.55.1; browser jobs use the matching mcr.microsoft.com/playwright:v1.55.1-noble image. This retains the previously tested browser version rather than silently upgrading graphics behaviour. The image supplies browser binaries and Linux dependencies; the project still installs its own pinned JavaScript packages. Setup-node selects Node 22 and caches npm downloads by lockfile.

The Linux harness uses Xvfb with Vulkan/SwiftShader flags inside the ephemeral test environment. These are CI-only launch settings, not instructions to weaken a user's browser. The image runs trusted project tests as root with sandbox disabled; do not repurpose it for arbitrary websites. Software rendering verifies correctness but says nothing about native GPU frame rate. Real-GPU/browser coverage remains a separate future validation layer.

The image is version-tagged, not digest-pinned, and Actions references still use major-version tags. Updating packages, the browser image or infrastructure should receive full validation. Image pulls and runner queues may outweigh savings for very small jobs. Three terrain jobs reduce critical-path time but can increase billed runner minutes; the pipeline promises selected coverage, not a universal speedup ratio.

10. Local and manual execution

npm ci --ignore-scripts
npm run check
npm run build
npm run check:site

# Linux: install the matched browser/dependencies once, outside the container.
npx playwright install --with-deps chromium
xvfb-run -a npm run test:smoke
xvfb-run -a npm run test:browser
xvfb-run -a node scripts/terrain-browser.mjs --group=edges
xvfb-run -a npm run test:terrain

# Collect every successful screenshot when investigating a regression.
ASTRAVA_SCREENSHOTS=all xvfb-run -a npm run test:terrain

On a desktop with a display, invoke the Node/npm scripts without xvfb-run. Build first because browser tests serve dist, not working-tree source files. A local build uses the local Git HEAD as its label even when the worktree is dirty; it is not a release attestation. CI builds a clean checked-out commit and records hashes. The optional ASTRAVA_CHROMIUM points to a local executable for diagnostics; CI uses the image-matched browser and does not set it.

From GitHub Actions, choose Astrava full regression to test a branch without publishing. Choose Astrava CI and Pages on main with force_full=true and publish=true for a deliberately exhaustive publication. Manual controls can widen tests but cannot narrow an automatically selected full plan. Artifact downloads and browser tests can also be rerun as failed jobs within the same run while the artifacts remain available.

For rollback, identify a known-good commit, revert the offending source changes on main, and allow the normal gates and publication flow to create a new release. Do not force-reset history or deploy an unverified directory. Export long-term releases separately if seven-day artifacts are insufficient. Workflow timeouts are hard failures: prepare 6 minutes, smoke 10, each terrain group 12, gate 3, deploy 10 and delivery 8.

12. Evidence and limits

Artifacts retained seven days: astrava-site, validation-plan, webgpu-smoke-evidence, one terrain-evidence artifact per group, and published-delivery-evidence. Browser JSON records the tested build, case labels, frame counts, logical/rendered tile counts, morph factors, coverage and failures. Representative screenshots remain available without saving every successful frame.

All original 67 terrain cases remain in the catalogue, now independently initialised and sharded. The CPU suites continue to cover mathematical properties beyond those images. This pipeline does not yet use direct GPU readback, per-vendor hardware runners, temporal image-difference metrics, exhaustive atmosphere tests, automatic rollback, cross-workflow artifact promotion or guaranteed execution-time budgets. Add those only when their risks justify their cost.
